# 人工退款与赠券（新规则，待正式部署）

正式站已部署旧版人工退款，数据库为 20261101_0006；退款开关关闭，新购暂停。
以下是本地更新后的规则，不代表正式站已生效。新版必须先在专用测试库验证，再备份并升级。

## 业务规则

- 退款由经营者人工审核，每笔金额精确到分；累计现金退款不得超过原订单尚未退款的实付金额。券抵扣金额不作为现金返还。
- 新退款固定不回收解读卡。已使用与未使用的卡均可经人工审核退款，账户剩余卡和已有报告保留。
- 每笔经人工审核且由微信确认成功的退款，额外赠送一张 50 元优惠券。有效期从本站确认成功并入账时起满 7 天，不按下周一截断。
- PROCESSING、ABNORMAL、CLOSED、超时或结果未确认时不赠券。重复回调、查询、提交只处理同一退款单，不重复赠券、不延长有效期。
- 每次经人工批准的分次退款均有自己的退款单和一张赠券；同一订单有未决退款时不能创建下一笔。
- 原来使用的券保留已使用状态；退款赠券是独立的新券，不覆盖每周一的券。
- 购买时自动优先使用最早到期、且距到期至少两分钟的可用券；每单只用一张，不能叠加。旧版客户端的单券字段继续兼容。

## 操作与一致性

只读管理后台保持只读。退款创建仍仅提供 Linux root CLI，没有用户或管理后台的 HTTP 退款创建接口。

1. preview：SELECT 核对，生成有效期 10 分钟的预览，列明金额、不回收卡、成功赠券规则。没有现金请求、卡扣减或赠券。
2. submit：确认预览后查询原支付并验签；加用户行锁再核对预览。先登记原退款单，再提交微信原路退款，使用固定退款单号避免重复现金请求。
3. 已验签的回调或查询确认 SUCCESS 后，在同一个数据库事务内记录成功、创建赠券和赠券审计。券以 source_refund_id 唯一约束保障不重发；存储失败则事务回滚，后续查询/回调可以补齐。
4. status 只读本站；sync 和后台补查仅 GET。超时不会换新单号重新退款，retry 仍需明确确认原退款单号及已验签的不存在结果。

旧版可能登记的回收卡记录仍按原记录对账，不改变历史账本；所有新预览拒绝非零回收张数。旧预览必须重新生成，不能沿用旧确认码。

## 升级与验证

迁移 20261101_0007 保留 weekly_coupons 和所有已使用券、订单引用：period_start 允许 NULL 供独立赠券使用，新增唯一 source_refund_id。每周券仍使用非空周起点及原来的用户/周唯一约束。不回填历史赠券，不提供删除金融券记录的 downgrade。

退款开关和原路回调配置保持原有保护。新购是否暂停与退款处理独立；有未决退款时不能停回调和补查。

本地 SQLite 验证重复成功、失败不赠券、事务回滚、七天到期、每周券共存、已用卡退款、券占用/释放/消费及迁移保留历史。MySQL 专用测试另验证并发成功只赠一次、退款与报告扣卡并发互不多扣等。所有测试使用合成用户与模拟微信应答，不执行真实退款或模型调用。

后续仍需：专用 MySQL 验证、新版生产部署、真实退款回调与赠券验收，以及用户购买记录的退款展示。商户平台直接退款不会自动导入本站，不要对同一订单重复走两条现金退款途径。
